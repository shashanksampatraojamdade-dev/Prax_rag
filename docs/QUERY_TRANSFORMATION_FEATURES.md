## 13. Query rewriting

**Problem.** Users ask vague, conversational questions — *"How do I fix that
error when logging into the portal?"* — whose wording rarely matches how the
answer is written in the knowledge base. Pronouns ("that error"), missing
subjects and casual phrasing all weaken both keyword and semantic retrieval.

**Change.** Before retrieval, the query is sent to the language model with an
instruction to rewrite it into **one clear, specific, self-contained** search
query: resolve vague references, expand abbreviations, name the subject
explicitly, and *do not answer*. The rewritten text replaces the raw question as
the retrieval query (the original is preserved for grounding the final answer).

**Example.**

| Input | Rewritten (search query) |
|---|---|
| `How do I fix that error when logging into the portal?` | `Troubleshooting guide for user login authentication errors on the employee portal` |

**Justification.** Explicit, keyword-rich queries align far better with document
phrasing, so the correct chunks surface higher in the similarity search. The
step is **fail-safe**: if the model errors or returns nothing usable, the
original query is used unchanged, so rewriting can never block retrieval.

**Code references.**
- `prax_qt/rewriting.py::rewrite_query` — builds the prompt, calls the model,
  normalises the output (`_clean` strips quotes / `Query:` labels), falls back to
  the original on failure.
- `prax_qt/pipeline.py::QueryTransformer.transform` — applies rewriting first and
  records `"rewriting"` in `applied` when the text actually changed.
- Toggle: `QTConfig.enable_rewriting` ← `Settings.enable_query_rewriting`
  (`ENABLE_QUERY_REWRITING`).

## 14. Query expansion

**Problem.** A single phrasing misses relevant chunks that use **synonyms,
acronyms or adjacent terminology**. A search for *"US passport rules"* should
also match documents that say *"United States passport renewal requirements"* or
*"State Department guidelines"*, but a literal query will not.

**Change.** After rewriting, the query is sent to the model to list closely
related terms, synonyms, expanded acronyms and adjacent concepts. These terms are
parsed, de-duplicated, capped at `max_expansion_terms`, and appended to the
rewritten query to form the final `search_query` that gets embedded and searched.

**Example.**

| Input | Expansion terms added |
|---|---|
| `US passport rules` | `United States passport renewal requirements`, `travel visa documentation`, `State Department guidelines` |

**Justification.** Widening the query's surface area raises **recall** — fewer
relevant chunks are missed because of vocabulary mismatch — while the embedding
search keeps precision reasonable by ranking on overall semantic similarity.
Expansion runs on the *rewritten* query (`QTConfig.expand_rewritten`) so the
added terms build on the clarified intent. It is also **fail-safe**: on model
error or empty output it contributes no extra terms.

**Code references.**
- `prax_qt/expansion.py::expand_query` — prompts the model and returns up to
  `max_terms` terms; `_parse_terms` splits on commas/newlines, strips numbering
  and quotes, drops the original query and duplicates.
- `prax_qt/pipeline.py::QueryTransformer._build_search_query` — concatenates the
  rewritten query with the expansion terms into the final search query.
- Toggles: `QTConfig.enable_expansion` ← `Settings.enable_query_expansion`
  (`ENABLE_QUERY_EXPANSION`); `QTConfig.max_expansion_terms` ←
  `Settings.query_expansion_terms` (`QUERY_EXPANSION_TERMS`).

## 15. Multi-query retrieval

**Problem.** Rewriting and expansion still produce **one** query vector. But a
document may phrase the same idea in a way that is semantically distant from the
user's wording, so a single vector search can systematically miss it — there is
no second angle of attack.

**Change.** The model generates several **alternative phrasings** of the
question, each approaching it from a different vocabulary or level of
specificity. The host embeds **each** phrasing, runs a separate similarity
search, and **merges** the hits — keeping the best (smallest) distance per chunk
— before taking the final `top_k`.

**Example.**

| Input | Alternative phrasings searched in parallel |
|---|---|
| `How do I lower server latency?` | `Ways to optimize server response times` · `Reducing network lag in databases` · `Best practices for server performance tuning` |

**Justification.** Multiple phrasings cover multiple regions of the embedding
space, so documents that only one phrasing would surface are now caught —
raising recall for questions that can be asked many ways. Merging by best
per-chunk distance keeps the final ranking clean and bounded to `top_k`. The
step is **fail-safe**: if generation fails, the base query is used alone.

**Code references.**
- `prax_qt/multi_query.py::generate_query_variations` — prompts for `count`
  phrasings; `_parse_lines` cleans numbering/quotes and drops the original and
  duplicates.
- `prax_qt/pipeline.py::QueryTransformer._build_search_queries` — assembles the
  de-duplicated probe list (primary query + variations + HyDE doc).
- Host-side merge: `app/services/rag.py::RAGService._retrieve` — embeds each
  probe, searches, and merges hits by best per-chunk distance.
- Toggles: `QTConfig.enable_multi_query` ← `Settings.enable_multi_query`
  (`ENABLE_MULTI_QUERY`); `QTConfig.multi_query_count` ←
  `Settings.multi_query_count` (`MULTI_QUERY_COUNT`).

## 16. HyDE (Hypothetical Document Embeddings)

**Problem.** A short question and the paragraph that answers it look very
different to an embedding model — a terse query seldom sits near the dense,
technical prose of the real answer. This "query–document asymmetry" hurts
retrieval for complex or rare questions (e.g. an obscure error code) where the
question shares little vocabulary with the answer.

**Change.** The model first drafts a **hypothetical ideal answer** — a short,
technical passage that *would* answer the question, written like an internal
doc. The host embeds **that passage** (not the raw question) and searches for
real documents whose tone and phrasing match it. The hypothetical text is a
search *probe only* and is never shown to the user.

**Example.** For *"Why do I get error X903 when syncing?"* the model writes a
2–4 sentence troubleshooting paragraph about likely causes and fixes; its
embedding then retrieves the real company docs that read like it.

**Justification.** Searching with an answer-shaped vector lands in the same
region of the embedding space as real answer passages, dramatically improving
recall on hard questions — even when the generated answer is factually wrong,
because it is only used to *locate* similar real content. It is **fail-safe**:
on model failure HyDE simply contributes no probe.

**Code references.**
- `prax_qt/hyde.py::generate_hypothetical_document` — prompts for a short
  hypothetical passage; returns `None` on empty/failed output.
- `prax_qt/pipeline.py::QueryTransformer.transform` — adds the HyDE document to
  `search_queries` and records `"hyde"` in `applied`.
- Host-side merge: `app/services/rag.py::RAGService._retrieve` (same multi-probe
  merge as multi-query).
- Toggle: `QTConfig.enable_hyde` ← `Settings.enable_hyde` (`ENABLE_HYDE`).

## 21. Query classification

**Problem.** One retrieval strategy does not fit every question. "Show me
invoice #4059" needs an exact record match, while "Why did sales drop last
month?" needs an analytical summary over many sources. Treating them the same
wastes effort and returns weaker results.

**Change.** Before retrieval the model labels the query as one of
`exact_lookup`, `semantic`, `analytical` or `multi_hop`. The label is surfaced as
`query_class` and used inside the pipeline (it gates multi-hop planning and feeds
routing) and by the host (to adapt retrieval/generation).

**Example.** `"Show me invoice #4059"` → `exact_lookup`; `"Why did sales drop
last month?"` → `analytical`.

**Justification.** Knowing the query *type* lets the system spend effort where it
pays off — skipping expensive multi-hop planning for a simple lookup, or biasing
toward summary retrieval for an analytical question. It is **fail-safe**:
defaults to `semantic` on model failure.

**Code references.**
- `prax_qt/classification.py::classify_query` — constrained to `CATEGORIES`;
  `_match` maps free-form output onto a known label.
- `prax_qt/pipeline.py::QueryTransformer.transform` — runs it first; the label
  gates technique 24 (multi-hop) and feeds technique 22 (routing).
- Toggle: `QTConfig.enable_classification` ←
  `Settings.enable_query_classification` (`ENABLE_QUERY_CLASSIFICATION`).

## 22. Adaptive query routing

**Problem.** An enterprise rarely has one knowledge source. A question about a
person's phone number belongs in the SQL employee directory; an IT issue belongs
in the Zendesk KB. Sending every query to the same store returns poor answers.

**Change.** Given the query and its classification, the model picks the single
best-fit route from the host-declared candidate list (`QTConfig.routes`). The
SDK stays backend-agnostic — it only *names* the route (`route`); the host
decides what that route does. With a single configured route it short-circuits.

**Example.** `"What is Jane Doe's phone number?"` → `sql_directory`; `"How do I
reset my VPN?"` → `zendesk`.

**Justification.** Routing to the authoritative source for each query type is the
single biggest lever on answer quality in a multi-store setup, and it keeps
irrelevant stores out of the results. It is **fail-safe**: falls back to the
first configured route on ambiguity or model failure.

> **In this app:** only one route (`knowledge_base`) is configured, so routing is
> **advisory** — the decision is logged and returned but retrieval always uses the
> pgvector store. Add routes via `QUERY_ROUTES` and branch on `route` to activate.

**Code references.**
- `prax_qt/routing.py::route_query` — short-circuits for 0/1 routes; `_match`
  maps output onto a configured route name.
- Toggles: `QTConfig.enable_routing` ← `Settings.enable_query_routing`
  (`ENABLE_QUERY_ROUTING`); `QTConfig.routes` ← `Settings.query_routes`
  (`QUERY_ROUTES`, comma-separated).

## 23. Query intent detection

**Problem.** The same topic can be asked for in different *shapes*: a single
fact, a short summary, a how/why explanation, or a side-by-side comparison. If
the system ignores the wanted format, it retrieves and generates the wrong shape
of answer (e.g. a prose blurb when the user wanted a comparison).

**Change.** The model classifies the answer format intent as `fact`, `summary`,
`explanation`, `comparison`, `list` or `other`, surfaced as `intent`. The host
can use it to bias retrieval (pull structured comparison data) and to steer the
generation prompt.

**Example.** `"Mac vs Windows for programming"` → `comparison`; `"What is the SLA
uptime target?"` → `fact`.

**Justification.** Matching answer *format* to user expectation markedly improves
perceived answer quality, and comparison/list intents benefit from retrieving
structured rather than narrative content. It is **fail-safe**: defaults to
`other`.

**Code references.**
- `prax_qt/intent.py::detect_intent` — constrained to `INTENTS`; `_match`
  normalises the model output.
- Toggle: `QTConfig.enable_intent_detection` ←
  `Settings.enable_intent_detection` (`ENABLE_INTENT_DETECTION`).

## 24. Multi-hop retrieval planning

**Problem.** Some questions can't be answered from one lookup because the answer
depends on an intermediate fact: *"Who is the manager of the person who wrote the
security policy?"* A single search for the whole sentence matches little, because
no one document states it directly.

**Change.** The model decomposes the question into an ordered list of standalone
sub-queries (`hops`). Each hop is added to the retrieval `search_queries`, so the
host gathers evidence for every step (e.g. find the author, then find the
manager). Planning is **gated by classification**: if the query was classified
and is *not* `multi_hop`, the planning call is skipped to save latency.

**Example.** `"Who is the manager of the person who wrote the security policy?"`
→ Hop 1: *find the security policy's author*; Hop 2: *find that author's
manager*.

**Justification.** Breaking a chained question into its steps retrieves the
intermediate evidence a single query would miss, which is the only way to answer
dependency questions. Gating on classification keeps the extra model call off the
hot path for the common single-hop case. It is **fail-safe**: on failure the
pipeline falls back to single-shot retrieval.

**Code references.**
- `prax_qt/multi_hop.py::plan_hops` — prompts for an ordered plan; `_parse_lines`
  strips `Hop N:` prefixes and numbering.
- `prax_qt/pipeline.py::QueryTransformer.transform` — gates on `query_class` and
  appends `hops` to `search_queries`.
- Host-side merge: `app/services/rag.py::RAGService._retrieve` (each hop is a
  probe in the merged search).
- Toggles: `QTConfig.enable_multi_hop` ← `Settings.enable_multi_hop`
  (`ENABLE_MULTI_HOP`); `QTConfig.max_hops` ← `Settings.max_hops` (`MAX_HOPS`).

- **Adapter:** `app/services/qt_adapters.py` — `settings_to_qt_config` maps the
  app's `Settings` to `QTConfig`; `build_query_transformer` returns a ready
  `QueryTransformer` (or `None` when `ENABLE_QUERY_TRANSFORMATION` is off).
- **Model:** `app/services/llm.py::LLMService.complete` satisfies the SDK's
  `LanguageModel` protocol, so the same Vertex Gemini client powers rewriting and
  expansion.
- **Integration point:** `app/services/rag.py::RAGService._transform` runs the
  transformer before `_retrieve`; the rewritten+expanded `search_query` is
  embedded, while the LLM still answers the user's **original** question.
- **Observability:** every `/query` and `/query/stream` response carries a
  `query_transformation` object and a `query_transform_ms` timing
  (`app/schemas/query.py`).
