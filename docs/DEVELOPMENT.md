# Prax RAG — Development & Code Review Guide

> **Auto-managed sections** (settings, routes, module map, dependencies) are
> generated by `scripts/gen_docs.py`. Run `make docs` after code changes so this
> guide stays in sync with the source.

## 1. Local setup

```bash
uv pip install -e .            # install project + deps into .venv
cp .env.example .env           # configure (Vertex project, models, DB)
make db-up                     # start pgvector (docker compose)
gcloud auth application-default login   # Vertex ADC credentials
make seed                      # load sample documents
make run                       # start API at http://localhost:8000
```

Common `make` targets:

| Target | Action |
|---|---|
| `make install` | `uv pip install -e .` |
| `make db-up` / `make db-down` | start / stop pgvector container |
| `make seed` | load sample documents |
| `make run` | run the FastAPI app (uvicorn, reload) |
| `make cli q="..."` | ask a question from the terminal |
| `make docs` | regenerate the auto sections of the guides |
| `make check` | regenerate docs and fail if they changed (CI guard) |

### Layer boundaries (what may import what)
- **api/** → services + schemas + db session. No direct SQL.
- **services/** → repositories + core. Encapsulate Vertex/business logic here.
- **repositories/** → db models/session only. All SQL / pgvector lives here.
- **core/** → no dependency on api/services/repositories (cross-cutting only).

## 6. Conventions

- **Python 3.12+**, type hints everywhere, `from __future__` not needed.
- Keep handlers thin — validation + delegation to a service.
- Raise `ValueError` / domain errors in services; translate to `HTTPException`
  in the route layer.
- Logging goes to **stderr** via `app/core/logging.get_logger`; never `print`
  in library code (scripts/CLI may print user-facing output).
- Secrets (DB password, project creds) come from env, never committed.

## 7. Code review checklist

Use this when reviewing a change:

**Correctness & safety**
- [ ] New external calls (Vertex, DB) are wrapped in the right service/repo layer.
- [ ] Embedding dimension matches `EMBEDDING_DIM`; model changes re-ingest data.
- [ ] SQL stays inside `repositories/`; no raw SQL leaks into services/routes.
- [ ] User input is validated via Pydantic schemas; errors return clear 4xx.
- [ ] No secrets, credentials, or project-specific tokens hard-coded.

**Architecture**
- [ ] Layer boundaries respected (see §2).
- [ ] Config read via `get_settings()`, not `os.environ`.
- [ ] New config has a default + is documented (re-run `make docs`).

**RAG quality**
- [ ] Retrieval changes preserve grounding + source citations.
- [ ] LLM prompt changes keep the context-only system instruction.
- [ ] Chunking changes consider overlap and max chunk size.

**Docs & tests**
- [ ] `make docs` was run and generated sections are committed.
- [ ] New endpoints/behaviour are reflected in the guides (prose sections).
- [ ] Manual verification steps noted in the PR (ingest → query flow).

## 8. Keeping docs in sync (automation)

`docs/ARCHITECTURE.md` and `docs/DEVELOPMENT.md` contain `AUTOGEN` marker blocks.
`scripts/gen_docs.py` introspects the live code (settings model, FastAPI routes,
module tree, `pyproject.toml` deps) and rewrites those blocks.

- After any code change affecting config, routes, modules, or deps:
  `make docs`
- In CI, run `make check` — it regenerates and fails if the committed docs are
  stale, forcing contributors to keep them current.

Hand-written prose (diagrams, rationale, checklists) lives **outside** the
markers and is never overwritten.
