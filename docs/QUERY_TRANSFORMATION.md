# PraxQT — Query Understanding & Transformation SDK

> **Scope:** Architecture of the `prax_qt` SDK — a **plug-and-play** query
> understanding & transformation layer for RAG. It is intentionally kept
> **separate** from the application architecture (`ARCHITECTURE.md`) and the
> knowledge-base quality log (`KB_IMPROVEMENTS.md`). The per-technique rationale
> and code references live in `QUERY_TRANSFORMATION_FEATURES.md`.
>
> The settings and module tables below are regenerated by `make docs`, so this
> guide never drifts from the code.

## 1. What it does

A user's phrasing rarely matches how answers are written in the knowledge base.
`prax_qt` sits **in front of retrieval** and reshapes each incoming query:

1. **Query rewriting** — turns a vague, conversational question into one clear,
   explicit, search-friendly statement.
2. **Query expansion** — enriches the query with synonyms, expanded acronyms and
   related concepts so relevant chunks are not missed.
3. **Multi-query retrieval** — generates several alternative phrasings of the
   question; the host searches each and merges the hits.
4. **HyDE** — drafts a hypothetical ideal answer and searches for real documents
   that look like it (bridging the query↔document vocabulary gap).
5. **Query classification** — labels the query `exact_lookup` / `semantic` /
   `analytical` / `multi_hop` to adapt the strategy.
6. **Adaptive routing** — picks the best-fit retrieval target from the host's
   candidate routes.
7. **Intent detection** — detects the answer format wanted (`fact` / `summary` /
   `explanation` / `comparison` / `list`).
8. **Multi-hop planning** — decomposes chained questions into ordered sub-queries
   (gated by classification).

Techniques 1–2 refine a **single** query string (`search_query`). Techniques
3, 4 and 8 are *retrieval-widening*: they emit extra **probes** in
`search_queries`, and the host embeds/searches each probe and merges the
results. Techniques 5–7 produce **advisory metadata** (`query_class`, `route`,
`intent`) the host can act on.

Enable the SDK and **every enabled technique is applied**, in order, to each
query. The *original* question is always preserved so the app can still show the
user their own words and ground the final answer on their true intent.

## 2. Design — dependency inversion (same pattern as `prax_kb`)

The SDK owns the **techniques**; the host owns the **model**. The only thing the
SDK needs from the host is "turn a prompt into text", expressed as the
`LanguageModel` protocol. Nothing in `prax_qt` imports Vertex, FastAPI, the DB,
or any app module — so any team can drop it into their own stack.

```
          ┌──────────────────────── host app (Prax RAG) ────────────────────────┐
          │                                                                      │
  query → │  RAGService._transform ──► QueryTransformer.transform(query)         │
          │        ▲                           │                                 │
          │        │ TransformedQuery          │ model.complete(prompt, system)  │
          │        │ (.search_query)           ▼                                 │
          │        │                   ┌─────────────────┐                       │
          │        └───────────────────│   prax_qt SDK   │                       │
          │                            │  rewriting +    │◄── LanguageModel ─────┤
          │                            │  expansion      │     (LLMService)      │
          │                            └─────────────────┘                       │
          │  search_query ──► EmbeddingService ──► VectorStore (pgvector)        │
          └──────────────────────────────────────────────────────────────────────┘
```

- **SDK side (`prax_qt/`)** — backend-agnostic, zero app imports.
- **Host side (`app/`)** — provides a `LanguageModel` adapter and maps settings.

### Integration contract

| Protocol | Method | Host adapter |
|---|---|---|
| `LanguageModel` | `complete(prompt, *, system=None) -> str` | `app/services/llm.py::LLMService.complete` |

Because `LLMService` already exposes `complete`, it satisfies the protocol
directly — no wrapper class is needed. `app/services/qt_adapters.py` only maps
`Settings → QTConfig` and builds the transformer.

## 4. Request flow in this app

1. `POST /api/v1/query` (or `/query/stream`) → `RAGService`.
2. `RAGService._transform` calls `QueryTransformer.transform(question)` when
   `ENABLE_QUERY_TRANSFORMATION` is on; otherwise it is a no-op passthrough.
3. `RAGService._retrieve` embeds **every probe** in `search_queries` (the primary
   rewritten+expanded query, plus multi-query variations and the HyDE document),
   runs a pgvector similarity search per probe, and **merges** the hits — keeping
   the best (smallest) distance per chunk — before taking the final `top_k`.
   (With only one probe it is a single plain search.)
4. The **original** question + retrieved context are sent to the LLM to generate
   the grounded answer.
5. The response includes a `query_transformation` object (original, rewritten,
   expansions, search_query, applied) and a `query_transform_ms` timing so the
   step is fully observable in Swagger and the UI.

### Performance — fast path + parallel fallback

Query understanding would otherwise cost one LLM round-trip per technique
(~8 sequential calls). Two optimisations keep it fast **and** accurate:

- **Single-call fast path** (`QUERY_SINGLE_CALL=true`, default): `prax_qt/planner.py`
  asks the LLM for one structured JSON object containing *all* enabled outputs
  (classification, intent, route, rewritten, expansions, variations, HyDE
  document, hops) in a **single** call. If the JSON fails to parse, the pipeline
  automatically falls back to the per-technique path — behaviour is never lost.
- **Parallel per-technique fallback** (`QUERY_MAX_WORKERS`, default 8): when the
  per-technique path runs, independent techniques execute concurrently in a
  thread pool across two dependency "waves" rather than one-after-another:
  - **Wave 1** (depends only on the query): classification, intent, rewriting.
  - **Wave 2** (depends on wave 1): routing (needs the class), expansion,
    multi-query, HyDE, multi-hop (needs the rewritten query + class gate).

  This collapses ~8 sequential round-trips into two while producing identical
  results. Set `QUERY_MAX_WORKERS=1` to force strictly-sequential execution.
- **Batch probe embeddings**: `RAGService._retrieve` embeds all probes in one
  Vertex call (`embed_queries`) instead of one call per probe.

### Accuracy — class-driven technique selection

Running *every* technique on *every* query hurts accuracy: query expansion and
HyDE inject synonyms and invented phrasing that pull irrelevant passages for an
exact-ID lookup, while multi-hop planning is wasted effort on a simple question.
So **classification (technique 21) acts as a relevance gate** that decides which
retrieval-shaping techniques actually run — raising precision *and* cutting
latency (fewer calls for simple queries). Rewriting, routing and intent are
always useful and are never gated.

| Query class | Techniques applied (besides rewriting / routing / intent) |
|---|---|
| `exact_lookup` | *none* — keep the precise rewritten query; add no synonym noise |
| `semantic` | expansion + multi-query + HyDE |
| `analytical` | expansion + multi-query + HyDE |
| `multi_hop` | expansion + multi-query + multi-hop planning |

The gate is applied in **both** paths: the single-call path strips the
not-useful outputs the planner returned (zero extra latency), and the parallel
path simply never submits those calls. When classification is disabled or
inconclusive, every enabled technique is allowed (previous behaviour). The
mapping lives in `prax_qt/pipeline.py` (`_CLASS_TECHNIQUES` /
`_relevant_techniques`); logs show `QT class=... gated out [...]` when it fires.

## 6. Using the SDK in another project

```python
from prax_qt import QueryTransformer, QTConfig

class MyLLM:                       # your model, any provider
    def complete(self, prompt, *, system=None) -> str:
        return my_client.chat(system=system, user=prompt)

qt = QueryTransformer(model=MyLLM(), config=QTConfig(max_expansion_terms=6))
result = qt.transform("how do I fix that login thing?")

hits   = my_retriever(result.search_query)       # embed & search THIS
answer = my_llm_answer(result.original, hits)    # ground on the REAL question
```

See `prax_qt/README.md` for the full quick-start.

## 7. Operational notes

- **Latency.** Each enabled technique is one (or more) model call: rewriting,
  expansion, multi-query and HyDE run sequentially, and multi-query/HyDE also add
  one embedding + vector search **per probe**. Budget accordingly and disable the
  heavier techniques (multi-query, HyDE) to trade recall for speed.
- **Fail-safe.** Every technique catches model errors and falls back (rewriting →
  original query, expansion → no terms, multi-query → no variations, HyDE → no
  probe), so a transient model hiccup never blocks retrieval.
- **Determinism.** Generation runs at low temperature; the SDK normalises and
  de-duplicates model output before building the search query.
